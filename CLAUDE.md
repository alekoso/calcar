# CalCar: правила проекту

## Про продукт

CalCar (calcar.io): платформа, яка допомагає зрозуміти, **чи варто брати саме це авто**. Це один рушій із трьома входами:

- **Import**: прорахунок пригону битого авто з аукціонів США (Copart, IAAI) в Україну: розбір пошкоджень за фото, кошторис запчастин і робіт, доставка, розмитнення, підсумок «під ключ».
- **Check**: незалежна перевірка будь-якого оголошення про продаж авто з будь-якої країни, не лише США: що це за машина, що з нею було, чи адекватна ціна, що перевірити перед покупкою.
- **Garage**: авто користувача та приватний журнал обслуговування.

Мова продукту: українська, з перекладами на російську та англійську. Спілкування з власником проекту: російською.

## Стек і структура

Статичні HTML-сторінки без збірки, серверна логіка: функції Vercel, дані: Supabase.

```
import.html           головна Import (вставити лот -> прорахунок)
result.html           звіт Import (найбільший файл, ~284 KB)
check.html            головна Check (вставити оголошення)
result-check.html     звіт Check
cabinet.html          кабінет: список звітів, памʼять помічника, акаунт
garage.html           гараж: авто користувача і журнал
config.js             ключі Supabase (НЕ ЧІПАТИ)
i18n/ru.js, en.js     словники перекладу
api/check.js          рушій Check
api/chat.js           чат-агент по конкретному авто (спільний для Check та Import)
api/memory.js         памʼять помічника про користувача
api/analyze.js        AI-розбір фото і кошторис (Import)
api/lot.js            дані лота з аукціону через Apify
api/check-translate.js, api/check-debug.js   допоміжні
vercel.json           маршрути
supabase.sql          основна схема БД
supabase-garage.sql   схема гаража
garagetest.js         тест збірки гаража
```

Код чату і памʼяті вбудований прямо у сторінки звітів, окремих підключень `<script src="/chat.js">` немає. Серверна частина живе тільки в `api/`: **функцією Vercel стає лише те, що лежить у цій папці**. Файл, покладений у корінь, мовчки не працює і дає 404 на своєму ендпоінті, тому нові серверні функції створювати одразу в `api/`.

Маршрути у `vercel.json`: `/` -> check.html, `/import`, `/check`, `/check/:id`, `/garage`, `/garage/:id`.

Сторінки викликають ці ендпоінти: `/api/analyze`, `/api/lot`, `/api/check`, `/api/check-translate`, `/api/chat`, `/api/memory`.

**Джерело правди про поточну реалізацію: код, а не ця документація.** Якщо файл насправді виглядає інакше, ніж описано тут, зупинись і скажи власнику про розбіжність, не підлаштовуйся мовчки.

## Жорсткі правила

1. **config.js ніколи не перезаписувати і не редагувати.** Там реальні ключі Supabase. Читати можна, змінювати ні. Ніколи не виводити вміст `config.js` у відповідь, діф, лог чи commit message.
2. **Довге тире (символ U+2014, em dash) заборонене** будь-де: у коді, текстах, інтерфейсі, коментарях. Замість нього двокрапка, кома або крапка з комою.
3. **Тести:** після кожної завершеної логічної зміни і обовʼязково перед комітом прогнати релевантні тести. Якщо для зміненої критичної логіки тесту немає, дописати мінімальний regression-тест у наявній архітектурі тестів. Не вигадувати беззмістовні тести заради самого правила.
4. **У кінці роботи показати явний список змінених файлів**, результат тестів і SHA коміту.
5. **Перед правкою прочитати файл**, а не покладатися на памʼять про його вміст. Файли великі, структура неочевидна: потрібну функцію чи селектор шукати пошуком, а не читати файл цілком без потреби.
6. **Імʼя конфігу: `window.CALCAR_SUPABASE`** (не CALCAR_CONFIG). Так читає кабінет і гараж.
7. **VIN у звітах лежить за шляхом `data->_meta->>vin`**, короткі посилання через `public_id`.
8. Правки робити **точковими** (заміна конкретного фрагмента), не переписувати великі файли цілком.
9. **Проект свідомо працює без frontend-фреймворка і без збірки.** Не додавати React, Vue, Vite, Next.js, Tailwind, npm-залежності чи новий build pipeline без прямого завдання власника.

## Git workflow

Claude Code має право самостійно вносити звичайні продуктові та UI-правки, запускати тести, робити коміт і push у `main`, якщо завдання явно поставив власник. Окремого підтвердження перед звичайним комітом питати не треба.

Перед початком роботи:

1. `git status --short`
2. переконатися, що немає несподіваних змін власника в робочому дереві;
3. `git pull --ff-only`;
4. перевірити поточну гілку і remote.

Після роботи:

1. прогнати тести;
2. `git diff --check`;
3. переглянути власний діф;
4. переконатися, що в коміт входять лише файли поточного завдання;
5. зробити зрозумілий коміт;
6. `git push origin main`;
7. повідомити власнику SHA коміту, список змінених файлів і результат тестів.

**Коміт у `main` одразу їде в продакшн:** Vercel деплоїть автоматично, проміжного середовища немає. Тому push робити тільки із зеленими тестами. Якщо після деплою знайдено поломку, відкат робиться через `git revert` окремим комітом, а не переписуванням історії.

Зупинитися і спитати власника, якщо:

- треба видалити дані або файли;
- потрібна зміна схеми продакшн-Supabase або destructive-міграція;
- зачіпаються авторизація, платежі чи безпека;
- у робочому дереві знайдено несподівані зміни;
- тести не проходять;
- виник git-конфлікт;
- завдання вимагає суттєвої зміни архітектури;
- gate чи передумова посилається на роботу, яку неможливо підтвердити текстом задачі або репозиторієм: зупинись і спитай, не заміняй її схожою на вигляд правкою.

Ніколи не використовувати `git push --force`, `git reset --hard`, `git clean -fd` та інші руйнівні git-команди без прямого дозволу.

## Міграції продакшн-Supabase

Claude Code може застосувати міграцію самостійно лише якщо вона одночасно:

- аддитивна (нові таблиці, колонки, індекси, bucket);
- backward-compatible: старий код і старі дані працюють без змін;
- не видаляє і не перейменовує наявні поля схеми;
- не переписує наявні дані (заповнення ПОРОЖНІХ нових колонок дозволене);
- не послаблює RLS чи доступ;
- покрита зеленими тестами і збережена SQL-файлом у репозиторії.

Destructive-міграції, перезапис даних, небезпечні зміни constraint-ів чи розширення доступу вимагають підтвердження власника. Контракт сховища Vehicle Memory: `docs/VEHICLE_INTELLIGENCE_STORAGE.md`.

Окремо про `config.js`: при першому запуску перевірити `git ls-files --error-unmatch config.js`. Якщо файл уже tracked, нічого самостійно не міняти і повідомити власнику. Якщо untracked, переконатися, що він у `.gitignore`. Не виконувати `git rm --cached config.js` самостійно.

## Стиль коду і текстів

- Тексти інтерфейсу українською, звертання на «ти» («Впиши ставку», «Додай авто»).
- Нові рядки інтерфейсу одразу додавати у `i18n/ru.js` та `i18n/en.js`. Динамічні рядки в JS проганяти через `window.t()`, інакше при виборі RU сторінка стане змішаною.
- Дизайн-токени вже визначені у `:root` кожної сторінки: лаймовий бренд `--brand:#B8F23D`, графіт `--ink:#141619`, фон `--bg:#F7F8F6`, висота шапки `--hdr-h:56px`, товщина її лінії `--hdr-line:1px`. Нові кольори не вигадувати.
- Шапка і меню акаунта мають бути однаковими на всіх шести сторінках: index, check, result, result-check, cabinet, garage. Пункти меню: Гараж, Звіти, Памʼять помічника, Налаштування акаунта.
- Звіти показують скелетон завантаження, поки дані не готові, і перемикаються в готовий стан одним додаванням класу `report-ready`. Не показувати порожній шаблон звіту.
- Помилки користувачу показувати людською мовою, без технічних деталей і кодів. Виняток: причина невдалого завантаження файлу, її корисно показати.

## Спільні блоки інтерфейсу

Частина спільних блоків (чат, памʼять, скелетон, шапка) історично продубльована всередині кількох HTML-файлів. Поки окремого завдання на рефакторинг немає:

- не переносити їх самостійно в нову архітектуру;
- змінюючи спільний блок, однаково змінити всі наявні копії;
- після зміни звірити копії між собою;
- не створювати третю реалізацію.

Винесення в спільний JS, CSS або компонент робити тільки окремим завданням.

## Дані автомобіля

За можливості нові функції мають привʼязувати дані до VIN або vehicle, а не створювати ізольовані дублікати.

Довгостроково CalCar формує Vehicle Graph: factory build, mileage observations, registration events, auction events, historical listings, historical photos, damage observations, Check-звіти, записи Garage.

Не копіювати одну й ту саму сутність у кілька незалежних форматів без потреби.

## Шар накопичення знань

Схема: `supabase-knowledge.sql` (застосовує власник вручну). Що де копиться:

- `option_dict` / `option_alias`: словник опцій (канонічні імена і синоніми).
- `equipment_observation` (+`_evidence`): спостереження комплектації конкретних
  VIN із кожного Check; ідемпотентні в межах снапшота, старі снапшоти ніколи
  не перезаписуються. ABSENT лише від джерела, здатного довести відсутність.
- `issue_observation` (+`_evidence`): ЛИШЕ vehicle-specific знахідки з
  первинним доказом (`event_key` = конкретна подія, `issue_key` = семантика
  проблеми). Типові слабкі місця моделі і generic-ризики сюди не пишуться.
- `observation_coverage`: чесний знаменник (visual завжди partial;
  повний перегляд галереї це окремий `gallery_complete`).
- `model_option_catalog` / `model_issue_catalog`: каталоги моделей, заповнює
  лише `knowledge-seed.js` (запуск руками), кожен факт із source_url і
  evidence_excerpt.
- `derived_option_stats` / `derived_issue_stats`: rebuildable кеш,
  перераховує `knowledge-recompute.js` (руками/розкладом, НЕ з Check);
  частоти по унікальних VIN.

Пише спостереження хук у `api/check.js` (writeKnowledge) після успішного
Check; помилка хука не ламає Check. Тести: `knowledgetest.js`.

## Стратегічний напрямок

CalCar будується не як локальний український VIN-checker, а як майбутня глобальна automotive intelligence platform.

Поточні продукти: Check, Import, Garage.

Довгострокові шари платформи:

- глобальні сторінки моделей і автомобільного ринку;
- CalCar Data: ціни, тренди, рейтинги та автомобільна аналітика по світу з фільтрами по країнах;
- Ask CalCar: автомобільний AI поверх структурованої automotive knowledge base;
- Vehicle Graph по VIN;
- Garage як постійний профіль автомобіля;
- пізніше продаж автомобіля та Market.

Дві базові сутності майбутньої платформи:

- **Model**: BMW X5 G05, Tesla Model Y тощо.
- **Vehicle**: конкретний автомобіль з конкретним VIN.

Це стратегічний контекст, а не поточний backlog. **Не реалізовувати ці функції без окремого завдання.**

## Принципи продукту

- **Якість розбору важливіша за економію.** Якщо вибір між дешевше і точніше, обирати точніше і сказати про це.
- **Чесна деградація:** показуємо те, що знайшли, і прямо кажемо, чого немає. Не вигадувати дані, яких не отримали.
- **Джерело кожного факту має бути зрозумілим.** Дані власника позначаються «Додано власником», офіційні факти аукціону відрізняються від припущень моделі.
- **Ризик і числа рахуються формулами**, а не «на думку моделі». Модель описує, код рахує.
- Не додавати функції «про запас». Якщо фічі немає в завданні, спитати, а не робити.

## Робочий контекст

Власник працює сам, без розробників, деплой автоматичний: коміт у `main` -> Vercel. Тариф Vercel Pro (ліміт функції 300 с). Помилки з проду він приносить текстом з Runtime Logs.
