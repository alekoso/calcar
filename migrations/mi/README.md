# Model Intelligence: міграції Phase 1

Фізична реалізація замороженої схеми: Architecture v1.1 (FROZEN), Physical
Schema v1 (FROZEN), Final Patch і поправка про межі KNOWN / OPEN / UNKNOWN.

Phase 1 створює лише структури. Model Intelligence до Check НЕ підключається.

## Порядок застосування

| Файл | Що створює |
|---|---|
| `001_schemas_enums_lookups` | схеми `mi` і `mi_vm`, 44 enum, 10 словників із seed |
| `002_subjects_hierarchy_source` | реєстр `knowledge_subject`, джерела, бренд, модельний ряд, покоління, версія, версія x ринок x рік |
| `003_components_equipment_state` | родини і варіанти компонентів, атрибути, аліаси, обладнання, доступність, комплектація версії, права, типи станів |
| `004_issue_maintenance_check` | проблеми, обслуговування, перевірки |
| `005_claims_applicability_evidence` | знімки публікації, клейми, предикати, звʼязки, докази, повторюваність |
| `006_staging` | кандидати і їхні докази |
| `007_mi_vm_interface` | розвʼязана ідентичність, стани компонентів, права, вимірювання, причини рішення |
| `008_fragments_packs_operations` | фрагменти версій, пакети знань, черга побудови |
| `009_validation_permissions` | міжтабличні сторожі, права, фінальна перевірка складу |

Відкат виконується у зворотному порядку файлами `*.down.sql`.

Порядок відрізняється від початкового плану у двох місцях, і обидва рази
через залежності: `mi.source` створюється у 02 (на нього посилаються аліаси
і комплектація з 03), а інтерфейс `mi_vm` створюється у 07 (на розвʼязану
ідентичність посилається пакет знань з 08).

## Як застосовувати

До Supabase застосовує ВЛАСНИК вручну, у порядку 001..009. Усі файли
аддитивні і ідемпотентні: повторний запуск нічого не ламає і не чистить
дані. Нічого існуючого не видаляється і не перейменовується.

`000_test_prelude.sql` до продакшну НЕ застосовується. Він потрібен лише
чистій локальній базі: створює заглушки `public.reports` і
`public.vehicle_snapshots`, які у продакшні вже існують і створені поза цим
репозиторієм.

## Тест

```
MI_TEST_DB_URL=postgres://localhost/calcar_mi_test node mitest.js
```

Тест проганяє повний цикл: застосування, повторне застосування,
позитивний smoke у транзакції з відкатом, негативні перевірки обмежень,
повний відкат, повторне застосування, фінальний відкат.

Тест ніколи не підключається до продакшну: адреса бази задається лише
змінною оточення.
