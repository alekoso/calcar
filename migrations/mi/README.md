# Model Intelligence: міграції Phase 1

Фізична реалізація замороженої схеми: Architecture v1.1 (FROZEN), Physical
Schema v1 (FROZEN), Final Patch і поправка про межі KNOWN / OPEN / UNKNOWN.

Phase 1 створює лише структури. Model Intelligence до Check НЕ підключається.

через залежності: `mi.source` створюється у 02 (на нього посилаються аліаси
і комплектація з 03), а інтерфейс `mi_vm` створюється у 07 (на розвʼязану
ідентичність посилається пакет знань з 08).

## Як застосовувати

До Supabase застосовує ВЛАСНИК вручну, у порядку 001..010. Усі файли
аддитивні і ідемпотентні: повторний запуск нічого не ламає і не чистить
дані. Нічого існуючого не видаляється і не перейменовується.

У цій теці лежать ЛИШЕ продакшн-міграції. Тестові фікстури живуть окремо,
у `tests/mi/fixtures/`, і до продакшну не застосовуються ніколи.

## Як публікується знання

Дослідження пише лише у staging: `mi.candidate_claim` і
`mi.candidate_evidence`. Далі:

```
mi.run_gate(candidate_id)                    -- перевірка якості, результат
                                             -- зберігається у gate_result
mi.publish_candidate(candidate_id, reviewer) -- атомарна публікація
```

Прямий INSERT опублікованого клейма відхиляється сторожем, а роль
`mi_ingest` не має на це прав. Публікація або проходить повністю, або не
лишає жодного рядка.

## Тести

```
MI_TEST_DB_URL=postgres://localhost/calcar_mi_test node mitest.js
MI_TEST_DB_URL=postgres://localhost/calcar_mi_test node milifecycletest.js
```

`mitest.js` перевіряє схему: застосування, повторне застосування, smoke
у транзакції з відкатом, негативні перевірки обмежень, повний відкат
і повторне застосування.

`milifecycletest.js` перевіряє життєвий цикл: staging і публікацію,
перевірки якості, атомарність, дедуплікацію і злиття, повторюваність
доказів, ревізії знання, інвалідацію фрагментів, успадкування і межі прав.

Обидва тести ніколи не підключаються до продакшну: адреса бази задається
лише змінною оточення.
