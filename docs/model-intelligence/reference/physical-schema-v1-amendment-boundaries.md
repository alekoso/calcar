# MODEL INTELLIGENCE PHYSICAL SCHEMA v1: AMENDMENT 1 (BOUNDARY KINDS) и FREEZE

Дата: 2026-09-11. Базис: Physical Schema v1 Design плюс Final Patch. Поправка одна, физическая. Архитектура не пересматривается, SQL не пишется, repo не меняется.

---

# 1. Проблема

В Final Patch (раздел B.3) все окна производства и доступности стали NOT NULL с сентинелами. Это убрало `coalesce` из ключей, но смешало два разных смысла в одном значении:

- «окно открыто»: вариант ставился с начала выпуска VMY и ставится до конца, граница отсутствует по существу;
- «граница неизвестна»: мы не установили дату, когда узел начали или перестали ставить.

Сентинел `9999-12-31` одинаково читался как «ещё выпускается» и как «дату окончания мы не нашли». Для оценщика это означало, что неизвестная граница давала MATCH, то есть нарушался главный инвариант: неизвестное не должно становиться подтверждённым.

---

# 2. Физическое представление

Для каждой границы диапазона добавляется парная колонка вида:

```
<name>      date NOT NULL
<name>_kind mi.boundary_kind NOT NULL
```

`mi.boundary_kind` это закрытый поведенческий enum из трёх значений: `known`, `open`, `unknown`.

Сентинелы сохраняются ради простоты индексов и сравнений, но получают однозначную привязку к виду границы. Нижний сентинел меняется с `1900-01-01` на `0001-01-01`, чтобы исключить совпадение с настоящей датой:

- `kind = 'known'`: колонка содержит реальную дату, не равную сентинелу;
- `kind = 'open'` или `kind = 'unknown'`: колонка содержит соответствующий сентинел (`0001-01-01` для нижней границы, `9999-12-31` для верхней).

Настоящие CHECK-ограничения (однострочные, immutable, выражаются обычным constraint):

- `CHECK ((from_kind = 'known') = (from_col <> DATE '0001-01-01'))`
- `CHECK ((to_kind = 'known') = (to_col <> DATE '9999-12-31'))`
- `CHECK (from_col <= to_col)`

Индексы не меняются: диапазонные сравнения по-прежнему идут по датам, вид границы читает только оценщик.

---

# 3. Семантика оценщика

Проверка «дата D принадлежит окну» возвращает одно из трёх значений.

Нижняя сторона:

| from_kind | Результат |
|---|---|
| known | определённо: `D >= from` или определённое нарушение |
| open | определённо удовлетворена |
| unknown | неопределённость |

Верхняя сторона симметрично.

Итог окна:

1. Есть определённое нарушение хотя бы с одной стороны (`D < from` при `from_kind='known'` или `D > to` при `to_kind='known'`): **NO_MATCH**. Определённое нарушение сильнее любой неопределённости с другой стороны.
2. Иначе обе стороны определённо удовлетворены (`known` с выполнением или `open`): **MATCH**.
3. Иначе (хотя бы одна сторона `unknown`, нарушений нет): **UNKNOWN**.

Совмещение с неточностью даты самого автомобиля (правило Appendix C v1.1: дата известна только с точностью до модельного года): MATCH только если определённость с обеих сторон, NO_MATCH при определённом непересечении, во всех остальных случаях UNKNOWN. Две неопределённости никогда не складываются в подтверждение.

Далее UNKNOWN ведёт себя как обычно: предикат даёт UNKNOWN, claim становится CONDITIONAL, а не APPLICABLE.

**Правило для предикатов.** В `mi.claim_applicability` границы диапазонов (`value_date_from/to`, `value_num_from/to`) допускают только `known` и `open`; `unknown` запрещён CHECK-ом. Если автор знания не установил границу, он не пишет диапазонный предикат вовсе, иначе предикат молча сузил бы или расширил применимость. Числовые границы используют `-Infinity` и `Infinity` вместе с тем же полем вида.

# 4. Затронутые таблицы

| Таблица | Окна | Новые колонки |
|---|---|---|
| `mi.generation` | prod_from, prod_to | prod_from_kind, prod_to_kind |
| `mi.version_market_year` | prod_from, prod_to | prod_from_kind, prod_to_kind |
| `mi.component_variant` | prod_from, prod_to | prod_from_kind, prod_to_kind |
| `mi.version_fitment` | prod_from, prod_to | prod_from_kind, prod_to_kind |
| `mi.equipment_availability` | sop_from, sop_to | sop_from_kind, sop_to_kind |
| `mi.claim` | effective_from, effective_to | effective_from_kind, effective_to_kind |
| `mi.claim_applicability` | value_date_from/to, value_num_from/to | value_from_kind, value_to_kind, только `known` и `open` |

Уникальные ключи не меняются: `version_fitment` по-прежнему UNIQUE (vmy_id, role_code, variant_id, prod_from), `equipment_availability` по-прежнему UNIQUE (vmy_id, item_id, sop_from); сентинел остаётся частью ключа и теперь однозначен.

Не затрагиваются: `mi_vm.component_state_instance.occurred_on` (наблюдение конкретной машины, отсутствие даты это NULL и вопрос provenance, а не applicability), `mi.source.published_at`, `mi_vm.measurement.expires_at`, служебные метки времени.

**Последствие для фрагмента.** Роль резолвится статически во фрагменте только тогда, когда у VMY ровно одна строка `version_fitment` для этой роли и обе её границы `known` или `open` и окно покрывает всё окно VMY. Если строк несколько или хотя бы одна граница `unknown`, роль помечается `vin_dependent` и разрешается на overlay по дате конкретной машины; при результате UNKNOWN роль остаётся `unresolved` и не становится `assumed_factory`.

# 5. Пример: неизвестная дата начала установки

**Tesla, ревизии 85 kWh пака.** В исследовании прямо зафиксировано, что карты «дата сборки в ревизию пака» с доказательствами нет. В схеме это строка:

```
version_fitment(vmy = P85D / US / 2015, role = battery_pack,
                variant = PACK_85_GEN1_REV_E,
                prod_from = 0001-01-01, prod_from_kind = unknown,
                prod_to   = 9999-12-31, prod_to_kind   = unknown)
```

Машина сборки 2015-03. Со старой моделью сентинелов окно читалось как `0001-01-01 .. 9999-12-31`, дата попадала внутрь, и ревизия E молча становилась подтверждённым фактом для любой P85D. С видами границ обе стороны дают неопределённость, окно возвращает UNKNOWN, строка fitment не резолвит роль. Роль `battery_pack` в слоте factory резолвится только более грубой строкой `PACK_85_GEN1` с границами `open/open`, покрывающими весь VMY. Claims, специфичные для ревизии E, остаются CONDITIONAL, а не фактами.

**BMW.** Дата, с которой ставился обновлённый электрический актуатор wastegate, в исследовании не установлена. Строка fitment для обновлённого варианта имеет `prod_from_kind = unknown`, поэтому claims об обновлённом актуаторе никогда не применяются к машине автоматически; применяются только claims уровня `N63B44O2`, а разрешение остаётся за диагностикой и документами.

**Porsche.** Дата перехода на корпус термостата с болтовым креплением трубок нам неизвестна. Fitment обновлённого корпуса имеет `prod_from_kind = unknown`: claims «обновлённая деталь уже стоит» не становятся применимыми по дате, они разрешаются документом о ремонте или осмотром, и до этого остаются CONDITIONAL.

Во всех трёх случаях неизвестная граница ведёт к проверке, а не к утверждению.

# 6. Обновление инвентаря словарей

Добавлен один закрытый поведенческий enum `mi.boundary_kind` (known, open, unknown): оценщик ветвится по значению. Итог: **21 enum и 10 lookup-таблиц**. Число таблиц не меняется: **52 CREATE NOW**, новых таблиц поправка не вводит.

Регрессионный тест к приёмочному набору (итого 51): **51. Unknown boundary.** Строка fitment с `unknown` границей не даёт MATCH ни для какой даты сборки; роль остаётся `unresolved`; ревизионно-специфичные claims получают CONDITIONAL, а не APPLICABLE и не APPLICABLE_ASSUMED.

# 7. Фиксация решений

- `mi.component_role.assumption_strength = 'strong'` для `engine`, `transmission`, `transfer_case`. Это зафиксировано для Schema v1: verification gap остаётся возможным для эндоскопии BMW и Porsche, строка допущения в identity_summary при этом обязательна.
- Все остальные заменяемые роли (`battery_pack`, `drive_unit_front`, `drive_unit_rear`, `mcu`, `adas_hw`, `charger`, `modem`, `suspension_system`, `brake_system`) сохраняют `weak`, как в Final Patch: допущение даёт APPLICABLE_ASSUMED, verification gap невозможен, MUST-проверка обязательна при importance не ниже 4.
- Нижний сентинел даты это `0001-01-01`; упоминание `1900-01-01` из Final Patch отменяется.

# 8. PHYSICAL SCHEMA v1: FROZEN

Состав заморожен и не подлежит импровизации при написании миграций:

52 таблицы в шести группах; 21 enum и 10 lookup-таблиц; пять результатов предиката и пять статусов claim; `component_role` с `is_replaceable` и `assumption_strength` (strong только для мотора, коробки и раздатки); evidence как единственная точка решения о bump ревизии; сентинелы с парными колонками вида границы (`known`, `open`, `unknown`); generated-колонки в `source` и `subject_alias`; суррогатный PK плюс UNIQUE expression index в `resolved_identity_dimension`; четыре триггер-валидации cross-table плюс один условный FK; `equipment_key` как identity оборудования; scope-aware алиасы с явным AMBIGUOUS; публикация только через `mi.publish_candidate`; отсутствие синхронной компиляции знаний в горячем пути Check; приёмочный набор из 51 golden retrieval test.

Любое изменение этого состава после заморозки оформляется отдельной поправкой с новым номером, а не правкой на ходу.
