# MI Research v1: Model Intelligence зростає з реальних Check

Статус: у продакшні з 2026-09-28. Міграція 028, модуль `api/mi-research.js`,
проводка в `api/check.js`.

## Петля

```
Check (VIN) -> mi_research_context: міст -> резолвер -> ідентичність -> пакет звіту
            -> наявне знання (плоский перелік) + ідентифікатори субʼєктів
  паралельно з декодом, історією, Vision:
            -> до 3 запитів Serper (найточніша підтверджена ідентичність, області без знання)
            -> до 4 джерел (один хост один раз, без площадок і соцмереж)
            -> один компактний виклик витягу: 0..2 важливі факти, яких MI не знає
  перед основним викликом (очікування не довше 3 с):
            -> блок MODEL_INTELLIGENCE + FRESH_WEB_FINDINGS у контекст звіту
  під час основного виклику:
            -> mi_research_persist: кандидат -> джерело/доказ -> mi.run_gate
               -> mi.publish_candidate (або злиття у наявний клейм) -> перезбірка фрагментів
  наступний Check тієї ж версії починає з багатшого MI.
```

Ручні картки каталогу лишаються еталоном і калібруванням; вони більше не
єдиний спосіб росту MI.

## Що робить код

- **MI спершу, веб потім.** `mi.research_context` повертає ідентичність
  (`identity_json`, `identity_summary`), плоский перелік уже відомого
  (issues, claims, check_items, maintenance, знання про саму версію з
  `comparisons`, entitlements) зі статусом застосовності, час останнього
  дослідження цієї ідентичності (max `created_at` кандидатів з extractor
  `check_research` на її субʼєктах; окремої таблиці немає) і число
  відкритих кандидатів.
- **Достатня ідентичність.** Дослідження іде лише коли підтверджена версія
  каталогу; інакше `version_not_identified` чи `brand_not_in_catalog`, і
  Check іде як раніше. Нічого не затягується заради ідентичності.
- **Запити.** Мітка = бренд + версія + розвʼязаний мотор + модельний рік
  (без повторів слів). Запит 1: загальні проблеми; запит 2: перша область
  (мотор, коробка, привід, шасі, електрика, кузов), якої у наявному знанні
  ще немає; запит 3: recall / service campaign / TSB для US чи невідомого
  ринку, інакше друга непокрита область.
- **Джерела.** Клас домену детермінований: регулятор (`.gov`, NHTSA, KBA)
  це `legal/primary`; домен виробника це `official/primary`; форуми це
  `owner/secondary`; магазини `vendor`; агрегатори `aggregator/low`. Решту
  класифікує модель, але підняти до official чи legal вона не може.
  Пріоритет відкриття: official і legal, потім невідомі, потім форуми.
- **Витяг.** Один виклик з `reasoning_effort low`, strict json_schema, до
  2 знахідок. Кожен доказ це цитата, яка мусить знайтися у тексті
  джерела (нормалізоване порівняння), інакше він відкидається; знахідка
  без доказу зникає. Нуль знахідок з поясненням `nothing_new_reason` це
  нормальний результат; квоти немає.
- **Область.** `component` лишається лише коли роль розвʼязана в
  ідентичності (confirmed чи assumed_factory), інакше знахідка звужується
  до `version`. На стороні бази `research_persist` повторно перевіряє це
  і привʼязує до варіанта тільки якщо він справді розвʼязаний; знахідка
  зі scope `vehicle` у MI не пишеться (`vehicle_scope_not_mi`).
- **Формулювання у звіті.** Блок несе силу доказу кожної знахідки:
  `documented` (official/legal) можна подавати як факт; `specialist`
  (першоджерело фахівців) як «фахівці описують»; `secondary` як «за даними
  фахових джерел»; `owner` лише «власники повідомляють». Правила блоку
  забороняють вигадувати поширеність і переносити знання з приміткою про
  іншу версію чи мотор.
- **Збереження.** Той самий gate, що і для ручних карток, без override.
  Той самий зміст на тому самому субʼєкті не створює другого кандидата:
  докази додаються до наявного відкритого і gate перевіряється знову.
  Публікація дубля зливається `publish_candidate` у наявний клейм. Після
  публікації всі інвалідовані фрагменти перезбираються у тому ж виклику.
- **Час.** Старт одразу після Vehicle Memory (ідентичність у памʼяті).
  Жорстка стеля 75 с, таймаути: пошук 6 с, джерело 8 с, витяг 40 с.
  Основний виклик чекає не довше 3 с; збереження чекається у кінці Check
  не довше 3 с; далі дослідження обривається сигналом. Фонового воркера
  немає: що не встигло, спробує наступний Check.
- **Вимикач.** `MI_RESEARCH=off`. Телеметрія у `_meta.mi_research`
  (запити, хости, класи джерел, знахідки без текстів джерел, результат
  збереження) і один рядок логу `[mi-research]`.

## Чого свідомо немає

- Дашбордів покриття, ротації доменів, планувальника, фонової черги.
- Окремої таблиці про «що вже досліджено»: cooldown 3 дні рахується з
  кандидатів; прогін без знахідок cooldown не створює, отже може
  повторитися наступним Check тієї ж версії.
- Платних обхідних шляхів для заблокованих джерел: таке джерело просто
  випадає.
- Запису VIN-специфічних веб-знахідок у Vehicle Memory: пошук іде за
  ідентичністю моделі, такі знахідки лишаються лише у контексті звіту.
- Захисту від одночасної публікації того самого факту двома Check у
  одну мілісекунду: `mi.claim.dedup_key` без unique-індексу; послідовні
  повтори зливаються.
